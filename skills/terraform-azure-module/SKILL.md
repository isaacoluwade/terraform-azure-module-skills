## Core Principles

1. **Security by default** — Private endpoints, public access disabled, secrets in Key Vault.
2. **Reusability** — A module is consumed across brands and environments (dev, qa, stage, prod).
3. **Separation of concerns** — A module owns its resource; authorization, identity, and networking are delegated to dedicated modules.
4. **Explicit over implicit** — Accept values as inputs. Never use `data` sources to look up values that the caller can provide.
5. **Consistency** — Every module follows the same patterns, conventions, and file structure.

## Module Naming

All modules use the form **`terraform-azurerm-<service-name>`**, for example `terraform-azurerm-storage-account` or `terraform-azurerm-key-vault`.

Modules are published to your organization's private registry: **`<your-terraform-registry>`**.

The repository name, the registry path, and the module's `source` URL all share this same name — there is no separate "internal" name.

## File Structure

```
terraform-azurerm-<service>/
├── docs/                           # Service documentation
│   ├── images/                     # Architecture diagrams (.drawio + .png)
│   └── ServiceDoc-<service>.md
├── examples/main/                  # Primary usage example
│   ├── locals.tf
│   ├── main.tf
│   ├── outputs.tf
│   ├── variables.tf
│   └── versions.tf
├── terratest/
│   ├── plan/                       # Test Terraform config
│   │   ├── main.tf
│   │   ├── outputs.tf
│   │   ├── variables.tf
│   │   └── versions.tf
│   └── test/                       # Go test files
│       ├── go.mod
│       ├── go.sum
│       └── terraform_test.go
├── .gitignore                      # .terraform/, *.tfstate*, *.tfplan, etc.
├── .pre-commit-config.yaml         # terraform fmt, docs, validate, tflint
├── azure-pipelines.yml             # CI/CD pipeline
├── CHANGELOG.md                    # Keep a Changelog format
├── README.md                       # Auto-generated by terraform-docs
├── VERSION                         # Semantic version (e.g., 1.0.0)
├── locals.tf                       # Location maps, primary_name, tags
├── main.tf                         # Core resource(s)
├── <logical-group>.tf              # diagnostics.tf, privatelink.tf, keyvault.tf, etc.
├── outputs.tf                      # Module outputs
├── variables.tf                    # Input variables
└── versions.tf                     # Provider + Terraform version constraints
```

A few non-obvious rules baked into this layout:

- `outputs.tf` is **plural**, never `output.tf`. Same for `variables.tf`.
- `versions.tf` (not `terraform.tf`) holds the `terraform {}` block and provider requirements.
- Use `main` as the resource label for the module's primary resource (e.g. `resource "azurerm_storage_account" "main"`), not `cluster01`/`vm01`.
- Group related resources into their own files (`diagnostics.tf`, `privatelink.tf`, `keyvault.tf`) instead of stuffing everything into `main.tf`.
- Use descriptive filenames (`keyvault.tf`, not `akv.tf`).

For a deep dive on the directory layout — including resource attribute ordering, when to split files, and rules for `examples/` and `terratest/` — see `terraform-module-structure`.

## Module Creation Workflow

1. Create the repo: `terraform-azurerm-<service-name>`.
2. Set up the file structure above (empty `.tf` files are fine to start).
3. Configure `.pre-commit-config.yaml` — `terraform fmt`, `terraform_docs`, `terraform_validate`, `tflint`. See `terraform-module-documentation`.
4. Define `versions.tf` — use `>=` (or `~>`) constraints, never static pins. See `terraform-provider-versioning`.
5. Define `variables.tf` — standard variables first, then module-specific. See `terraform-variable-design`.
6. Define `locals.tf` — standard locals required (see below). See `terraform-locals-patterns`.
7. Implement `main.tf` — use `main` as the resource label for the primary resource.
8. Add logical-group files as needed (`diagnostics.tf`, `privatelink.tf`, etc.).
9. Define `outputs.tf` — see `terraform-module-outputs`.
10. Write a runnable example under `examples/main/`.
11. Write Terratest plan + tests using `<your-terratest-helpers>`. See `terraform-module-testing`.
12. Write a ServiceDoc under `docs/`. See `terraform-module-documentation`.
13. Configure the pipeline in `azure-pipelines.yml`. See snippet below.
14. Create `VERSION` (start at `1.0.0`) and `CHANGELOG.md`. See `terraform-module-versioning`.
15. Generate the README: `terraform-docs markdown table . --output-file README.md`.
16. Submit a PR for certification review. See `terraform-azure-module-review`.

## Standard Variables (Every Module)

Every module declares these inputs. Copy this block as-is — the names, validation, and types are intentionally consistent across modules so callers can wire them up identically every time.

```hcl
variable "brand" {
  description = "The brand code (e.g., acme)."
  type        = string
  validation {
    condition     = can(regex("^[a-zA-Z0-9]+$", var.brand))
    error_message = "Brand must be alphanumeric."
  }
}

variable "environment" {
  description = "Target environment (dev, qa, stage, prod)."
  type        = string
  validation {
    condition     = contains(["dev", "qa", "stage", "prod"], var.environment)
    error_message = "Environment must be dev, qa, stage, or prod."
  }
}

variable "project_name" {
  description = "Project name used in resource naming."
  type        = string
}

variable "costcenter" {
  description = "Cost center code for billing."
  type        = string
  validation {
    condition     = can(regex("^[0-9]+$", var.costcenter))
    error_message = "Cost center must be numeric."
  }
}

variable "projectcode" {
  description = "Project code for tracking."
  type        = string
}

variable "location" {
  description = "Azure region for resource deployment."
  type        = string
  default     = "eastus"
}

variable "resource_group_name" {
  description = "Name of the resource group."
  type        = string
}

variable "tags" {
  description = "Additional tags to merge with default tags."
  type        = map(string)
  default     = {}
}
```

For the rules that govern *module-specific* variables (heredoc descriptions, `default = {}` + `nullable = false`, `optional()` defaults, `name_override`, sensitivity, validation), see `terraform-variable-design`.

## Standard Locals (Every Module)

Every module declares these locals. They convert the location code into a human-readable name, build the shared `primary_name` used by every resource, and produce the merged tag map.

```hcl
locals {
  location_map = {
    "eastus"      = "east us"
    "eastus2"     = "east us 2"
    "westus"      = "west us"
    "westus2"     = "west us 2"
    "centralus"   = "central us"
  }

  location_code_map = {
    "eastus"    = "eu"
    "eastus2"   = "eu2"
    "westus"    = "wu"
    "westus2"   = "wu2"
    "centralus" = "cu"
  }

  location      = local.location_map[var.location]
  location_code = local.location_code_map[var.location]

  primary_name   = "${var.brand}-${var.project_name}-${var.environment}-${local.location_code}"
  module_version = chomp(file("${path.module}/VERSION"))

  default_tags = {
    Brand          = var.brand
    Environment    = var.environment
    ProjectCode    = var.projectcode
    CostCenter     = var.costcenter
    deployed_using = "terraform/modules/terraform-azurerm-<service>/${local.module_version}"
  }

  tags = merge(local.default_tags, var.tags)
}
```

For deeper rules on locals (no pass-through locals, when to use `try()`/`lookup()`, tag-merging order, `module_version` patterns), see `terraform-locals-patterns`.

## Resource Naming Convention

Azure resource names follow `${local.primary_name}-<suffix>`. HCL identifiers (resource labels, variable names, output names) use `snake_case`. Azure resource names use lowercase with hyphens.

| Resource Type   | Suffix          | Example                  |
|-----------------|-----------------|--------------------------|
| Key Vault       | `-kv`           | `acme-myapp-dev-eu-kv`   |
| Storage Account | `st` (no dash)  | `acmemyappdeveust`       |
| AKS Cluster     | `-aks`          | `acme-myapp-dev-eu-aks`  |
| Subnet          | `-snet`         | `acme-myapp-dev-eu-snet` |
| NSG             | `-nsg`          | `acme-myapp-dev-eu-nsg`  |
| App Gateway     | `-gw`           | `acme-myapp-dev-eu-gw`   |

For the full naming reference (Azure character/length limits, suffix conventions per service, output names, infoblox record names), see `terraform-resource-naming`.

## Critical Anti-Patterns

| #  | Anti-Pattern                                  | Correct Approach                                           |
|----|-----------------------------------------------|------------------------------------------------------------|
| 1  | Using `data` sources to look up values        | Pass values explicitly as variables                        |
| 2  | Creating SPNs inside modules                  | SPNs are centrally managed; accept credentials as inputs   |
| 3  | Static provider versions (`= 4.0.0`)          | Use `>= 4.0.0` (or `~>`) in modules                        |
| 4  | `default = null` for complex objects          | Use `default = {}` + `nullable = false`                    |
| 5  | `default = ""` for optional strings           | Use `default = null`                                       |
| 6  | `coalesce(try(..., null), ...)`               | Use `try()` directly                                       |
| 7  | Numbered resource names (`cluster01`)         | Use `main` for the primary resource                        |
| 8  | Role assignments inside the module            | Delegate to a dedicated authorization module               |
| 9  | Module-name prefix on outputs                 | `cluster_id`, not `aro_cluster_id`                         |
| 10 | `sensitive = false` on variables              | Omit it entirely (`false` is the default)                  |
| 11 | Hardcoded values in resources                 | Parameterize anything that could vary across deployments   |
| 12 | `lower()`/`upper()` wrapping variable values  | Add regex validation to the variable instead               |
| 13 | Comments / commented-out code                 | Remove dead code entirely                                  |

The deeper "why" for each item — and how to spot them in review — lives in `terraform-azure-module-review`.

## Common Mistakes

1. **Skipping the standard variables.** Approximating them or renaming them — copy the block as-is so every module looks the same to its callers.
2. **Skipping the standard locals.** `primary_name`, `default_tags`, and `tags` are how every resource gets its name and tags; missing them creates inconsistent infrastructure.
3. **Reaching for `data` sources.** If the caller could pass it, accept it as a variable. Data lookups create runtime coupling and slow down `plan`.
4. **Naming the primary resource something other than `main`.** Reviewers and consumers expect `azurerm_<type>.main`.
5. **Pinning provider versions inside the module.** Modules use `>=` or `~>`; only root modules pin.
6. **Putting everything in `main.tf`.** Move grouped concerns (`diagnostics.tf`, `privatelink.tf`, `keyvault.tf`) into their own files.
7. **Output names prefixed with the module name** (`aro_cluster_id` instead of `cluster_id`). The module name is already the namespace.
8. **Defaulting optional strings to `""`.** Use `null` so Terraform treats them as unset.
9. **`default = null` for complex objects.** Use `default = {}` with `nullable = false` so callers always get a predictable shape.
10. **Forgetting the `examples/main/` and `terratest/` directories.** They are part of the module contract, not optional extras.
