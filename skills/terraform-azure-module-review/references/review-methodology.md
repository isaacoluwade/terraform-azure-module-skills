# Review Methodology: Five-Pass Analysis

This document defines the systematic approach for reviewing Terraform Azure module PRs. Each pass builds on the previous one. Do not skip passes — cross-cutting issues in later passes often reveal problems that file-level analysis misses.

---

## Before You Start

### Determine Review Context

Ask these questions before writing a single finding:

1. **What version is this?**
   - `1.0.0` (new module / initial certification) — Zero tolerance. No deferred work.
   - Minor/patch update — Check for breaking changes (see Breaking Changes section in Pass 4).
   - Major update — Breaking changes allowed but must be documented.

2. **Is this a full module or a patch?**
   - Full module: review everything end-to-end.
   - Patch: focus on changed files, but verify cross-cutting impacts.

3. **What Azure service does this manage?**
   - Load the service-specific patterns from the `terraform-azure-patterns` skill.
   - Understand the service's key constraints (naming limits, regional availability, RBAC model).

4. **What files are changed?**
   - Map the changed files to determine which review passes need deep focus.
   - If `variables.tf` changed — deep variable analysis.
   - If `main.tf` changed — deep resource logic analysis.
   - If `versions.tf` changed — provider constraint analysis.

### Load Standards

Read these topical skills in this collection based on the files being reviewed:

- Always read: `terraform-variable-design`, `terraform-locals-patterns`, `terraform-module-structure`, `terraform-resource-naming`.
- If resources changed: `terraform-azure-patterns`, `terraform-style-and-formatting`.
- If outputs changed: `terraform-module-outputs`.
- If providers changed: `terraform-provider-versioning`.
- If tests changed: `terraform-module-testing`.
- If docs changed: `terraform-module-documentation`, `terraform-module-versioning`.

## Pass 1: Structural Scan

**Goal:** Verify the module has the correct files, layout, and naming before diving into code.

**Time:** Quick scan — this should take seconds, not minutes.

### Checklist

```
[ ] Repository named terraform-azurerm-<service-name>
[ ] All required files present:
    - variables.tf
    - outputs.tf
    - locals.tf
    - main.tf
    - versions.tf
    - VERSION
    - CHANGELOG.md
    - README.md (auto-generated by terraform-docs)
    - .gitignore
    - .pre-commit-config.yaml
    - azure-pipelines.yml
    - examples/main/  (primary example)
    - terratest/plan/  (test Terraform config)
    - terratest/test/  (Go test files)
    - docs/ServiceDoc-<service>.md
[ ] No unexpected files:
    - No terraform.tf (use versions.tf)
    - No leftover .shellcheckrc without .sh files
    - No Makefile without make targets
    - No helpers/ or scripts/ unless actively used
    - No *.tfstate*, *.tfplan, .terraform/ committed
[ ] Logical grouping files appropriately named:
    - authorization.tf, keyvault.tf, diagnostics.tf, privatelink.tf, infoblox.tf, etc.
    - NOT resource-type names like azurerm_key_vault.tf
[ ] VERSION file contains valid semver (1.0.0+ for certified modules)
[ ] .gitignore includes: .terraform/, *.tfstate*, *.tfplan, .terraform.lock.hcl
```

### What to Question

- **Missing files:** Is there a ServiceDoc? Architecture diagram? If not, why?
- **Extra files:** Any file that doesn't serve a clear purpose should be challenged.
- **File naming:** `terraform.tf` should be `versions.tf`. `provider.tf` content belongs in `versions.tf`.

For full structural rules, see the `terraform-module-structure` skill.

## Pass 2: Standards Compliance

**Goal:** Verify every variable, local, output, and provider constraint follows the standards in the topical skills exactly.

**Time:** This is the most time-intensive pass. Be thorough.

### 2a: Variables Review

For each variable, verify:

```
Standard variables (must be present with exact validation):
[ ] brand              no default, regex validation for alphanumeric
[ ] environment        no default, contains() validation for dev/qa/stage/prod/sandbox
[ ] project_name       no default, regex validation
[ ] costcenter         no default, regex validation for numeric
[ ] projectcode        no default
[ ] location           default = "eastus"
[ ] resource_group_name no default, regex validation
[ ] tags               default = {}, type = map(string)

For each module-specific variable:
[ ] Has a description (ending with period)
[ ] Complex objects use heredoc <<-EOT description with per-attribute docs
[ ] Complex objects have default = {} and nullable = false
[ ] Optional string attributes default to null, not ""
[ ] Has validation {} blocks for all constrained inputs
[ ] No sensitive = false declarations (remove — it's the default)
[ ] sensitive = true only on genuinely sensitive fields (not whole objects mixing sensitive and non-sensitive)
[ ] Related attributes grouped into objects (not scattered as separate variables)
[ ] Attribute descriptions use (Optional) and (Required) prefixes
[ ] Values in descriptions are highlighted with backticks
```

**Key question for every variable:** "Is this the simplest possible interface for the consumer?"

If a variable has 8+ attributes, ask whether it should be split. If multiple variables share a prefix (`master_subnet_id`, `master_vm_size`, `master_disk_size`), ask whether they should be an object.

For full variable design rules, see the `terraform-variable-design` skill.

### 2b: Locals Review

```
Standard locals (must be present):
[ ] location_map         maps short names to display names
[ ] location_code_map    maps to region codes
[ ] location = local.location_map[var.location]
[ ] location_code = local.location_code_map[var.location]
[ ] primary_name = "${var.brand}-${var.project_name}-${var.environment}-${local.location_code}"
[ ] module_version = chomp(file("${path.module}/VERSION"))
[ ] default_tags         Brand, Environment, ProjectCode, CostCenter, deployed_using
[ ] tags = merge(local.default_tags, var.tags)   <-- ORDER MATTERS: user tags override defaults

Format checks:
[ ] deployed_using = "terraform/modules/terraform-azurerm-<service>/${local.module_version}"
[ ] No lower() wrapping on primary_name or any local derived from validated inputs
[ ] No pass-through locals (a local that just echoes a variable unchanged)
[ ] No coalesce(try(..., null), ...) — use try() or lookup() directly
```

**Key question for every local:** "Does this local compute something, or is it just passing a value through?" Pass-throughs add noise — either transform the value or use the variable directly.

For full locals rules, see the `terraform-locals-patterns` skill.

### 2c: Outputs Review

```
[ ] No module-name prefix (cluster_id, NOT aro_cluster_id)
[ ] All descriptions end with a period
[ ] Conditional outputs use try() — e.g., try(resource.name[0].attribute, null)
[ ] No redundant ternary: var.enabled ? try(x[0].y, null) : null — just use try()
[ ] Sensitive outputs marked sensitive = true
[ ] No sensitive = false declarations
[ ] Complex outputs use heredoc descriptions
[ ] All outputs needed for testing are exposed
```

For full output rules, see the `terraform-module-outputs` skill.

### 2d: Providers Review

```
[ ] versions.tf (NOT terraform.tf)
[ ] required_version = ">= X.Y.Z" declared
[ ] Provider constraints use >= or ~> (NOT static = versions)
[ ] No provider configuration block in the module (only in root/example modules)
[ ] No unnecessary providers declared (every declared provider must be used)
```

For full provider versioning rules, see the `terraform-provider-versioning` skill.

## Pass 3: Logic & Correctness

**Goal:** Find bugs that will cause runtime failures or incorrect behavior.

This is where expert review separates from checklist review. You're looking for logic errors, not style issues.

### 3a: Conditional Resource Guards

This is the #1 source of Critical bugs. For every boolean toggle in the module:

```
1. Find the toggle variable (e.g., var.keyvault.enabled, var.dns.infoblox_enabled)
2. Trace EVERY resource, data source, and module call that depends on this feature
3. Verify EACH one has a matching count or for_each guard
4. Verify ALL references to guarded resources use [0] indexing or try()
5. Verify null propagation: when the feature is off, are the inputs to guarded
   resources also null-safe? (e.g., key_vault_id = var.keyvault.resource_id when
   keyvault is disabled — resource_id will be null)
```

**The complete chain must be guarded.** If a data source creates data used by a resource, and the resource has a count guard, the data source needs a count guard too. If a local references a guarded resource, the local needs a `try()` or conditional.

### 3b: Null Safety in for_each and Role Assignments

```
[ ] for_each maps don't contain null values as keys
[ ] for_each maps with optional scope values filter out nulls:
    { for k, v in map : k => v if v != null }
[ ] Role assignment scopes are never null (causes authorization module failure)
[ ] for_each keys are stable — adding/removing items doesn't cause unrelated recreation
[ ] No hardcoded keys like "cluster01-subnet-contributor" — derive from variables
```

### 3c: Data Source Risks

For every `data` block:

```
[ ] Why is this a data source and not a variable input?
    - If the answer is "convenience," it should be a variable
    - If the answer is "we need a computed attribute not available as input," document why
[ ] Does the data source have a count guard if it's conditional?
[ ] What happens if the data source returns no results? Is there error handling?
[ ] Does the data source create an implicit dependency that affects plan ordering?
```

### 3d: State Safety

```
[ ] No resources renamed without moved blocks
[ ] No count <-> for_each changes without state migration plan
[ ] No variable type changes that would break existing .tfvars
[ ] No variable removals without deprecation notice
[ ] lifecycle ignore_changes targets specific attributes, not entire blocks
[ ] lifecycle prevent_destroy NOT used in modules (use Azure management locks)
[ ] Dynamic blocks don't create phantom state entries when empty
```

### 3e: Value Semantics

```
[ ] null vs "" — are they being used with correct semantics?
    - null = "not set, use the default behavior"
    - "" = "set to empty string" (usually wrong for Terraform)
[ ] String values that should be validated aren't wrapped in lower()/upper()
[ ] try() fallback values match the expected type (no try(string_value, []) mismatches)
[ ] coalesce() not used where any argument could be "" (coalesce treats "" as falsy)
[ ] Sensitive values actually resolved from Key Vault, not passed as plaintext variables
[ ] Identity variables use KV secret names (not raw credential values)
```

### 3f: Data Flow Tracing for Critical Findings

This is the technique that separates expert reviews from checklist reviews. For any variable with a questionable default or missing validation:

```
1. Start at the variable definition (e.g., var.vnet_id with default = "")
2. Trace through locals — what transforms this value? Does it end up in a map?
3. Trace into resources — what block/argument receives this value?
4. Predict the runtime behavior — will the provider API accept this value?
5. Predict the error message — will the consumer understand what went wrong?
```

**If the trace ends at a provider API call with a bad value that produces a confusing error, that's Critical.** The severity is about the IMPACT (runtime failure with bad error message), not the ROOT CAUSE (wrong default). The root cause might only be Major on its own, but the downstream impact elevates it.

**Example of a good Critical finding:**

> `vnet_id` defaults to `""` -> flows into `local.role_assignments` map -> feeds `for_each` on `azurerm_role_assignment` -> Azure API receives `scope = ""` -> cryptic 400 error at apply time. Consumer has no idea what went wrong.

**Example of a bad Critical finding:**

> Standard variables have wrong defaults and VERSION file is missing.

That bundles unrelated issues. The variable defaults might be Major, the VERSION file is Minor. Neither is Critical on its own unless you trace the impact.

## Pass 4: Architecture & Design

**Goal:** Evaluate whether the module's design follows the architectural principles in this skill collection.

### 4a: Responsibility Boundaries

```
[ ] Module owns exactly ONE Azure resource type (plus supporting resources)
[ ] RBAC/role assignments — delegated to the authorization module
[ ] Service principal management — centralized repo, NOT in this module
[ ] Identity — Managed Identity preferred over SPN where possible
[ ] Networking resources — accepted as inputs (resource IDs), not created
[ ] Diagnostic settings — separate file if present (diagnostics.tf)
[ ] Private endpoints — separate file if present (privatelink.tf)
[ ] DNS records — separate file if present (infoblox.tf, dns.tf)
```

### 4b: Consumer Experience

Think like a consumer of this module who reads the README and examples:

```
[ ] Can a consumer deploy this module by filling in ONLY the required variables?
[ ] Are optional features clearly toggleable (e.g., enabled = true/false)?
[ ] Does the default behavior make sense? (secure, minimal, production-safe)
[ ] Are variable names intuitive? Would a consumer guess wrong about what they mean?
[ ] Does the example actually work if you copy-paste it?
[ ] Are there any "magic values" that a consumer wouldn't know?
    (e.g., aro_rp_object_id defaulting to a specific GUID — document it!)
[ ] name_override pattern available for import/migration support?
```

### 4c: Patterns and Anti-Patterns

```
Anti-patterns (always flag):
[ ] data sources used for values that should be inputs
[ ] SPN creation inside the module
[ ] Role assignments inside the module (not via authorization module)
[ ] Static provider version pins (= X.Y.Z)
[ ] default = null on complex objects (should be {} + nullable = false)
[ ] default = "" on optional strings (should be null)
[ ] Numbered resource names (cluster01, vm01)
[ ] Module-name prefix on outputs
[ ] sensitive = false declarations
[ ] Comments/commented-out code left in
[ ] lower() wrapping validated inputs
[ ] Hardcoded values that should be parameterized
[ ] Cross-cutting concerns baked in (antimalware, monitoring agents) vs Azure Policy

Positive patterns (acknowledge):
[ ] main as single resource label
[ ] try() for conditional output access
[ ] Logical file grouping (authorization.tf, keyvault.tf, etc.)
[ ] Proper count/for_each guards on conditional resources
[ ] default = {} + nullable = false on complex variables
[ ] Standard variable/local patterns used exactly
[ ] Clean separation of concerns
```

### 4d: Breaking Change Detection

For PRs on existing modules (not 1.0.0 initial certification):

```
For minor/patch versions, ALL of these are BREAKING and require a major version bump:
[ ] New resource without creation toggle (count = var.create_x ? 1 : 0)
[ ] New required variable (no default)
[ ] Variable type change
[ ] Variable default change
[ ] Variable rename or removal
[ ] Output removal or value change
[ ] Output sensitive flag change
[ ] Resource rename without moved block
[ ] count <-> for_each conversion
[ ] nullable true -> false change
[ ] Adding non-default arguments to existing resources
[ ] Adding nested blocks without dynamic
```

For full versioning rules, see the `terraform-module-versioning` skill.

## Pass 5: Cross-Cutting Concerns

**Goal:** Check testing, documentation, pipeline, security, and examples.

### 5a: Testing

```
[ ] Uses the standard Terratest framework (latest version)
[ ] Standard plan/ + test/ directory structure
[ ] Test uses module outputs for assertions (not hardcoded values)
[ ] Different behaviors tested (not the same feature multiple times)
[ ] Test plan doesn't create SPNs if avoidable
[ ] Test variables are correctly typed (string "9100021" not number 9100021)
[ ] go.mod references the latest test framework version
```

For full testing rules, see the `terraform-module-testing` skill.

### 5b: Documentation

```
[ ] CHANGELOG.md follows Keep a Changelog format
[ ] Entries in imperative mood ("Add", "Fix", "Remove" — not "Added", "Fixed")
[ ] Breaking changes prefixed with **Breaking:**
[ ] README.md auto-generated by terraform-docs (not hand-written)
[ ] ServiceDoc present and comprehensive
[ ] Architecture diagrams in docs/images/ (.drawio + .png)
```

For full documentation rules, see the `terraform-module-documentation` skill.

### 5c: Pipeline

```
[ ] azure-pipelines.yml uses the shared module template:
    extends:
      template: terraform/terraform_module.yml@<your-templates>
[ ] Trigger includes feature/*, bugfix/*, hotfix/* branches (not just main)
[ ] TerraformVersion and GoVersion parameters specified
```

### 5d: Examples

```
[ ] Primary example in examples/main/ (not examples/sample-cluster or similar)
[ ] Example has complete file set: locals.tf, main.tf, outputs.tf, variables.tf, versions.tf
[ ] Example variables are SIMPLE — just `variable "brand" {}` without types/descriptions/validation
[ ] Provider versions in examples are pinned exactly (e.g., = 4.65.0)
[ ] No real values in examples (GUIDs, subscription IDs, etc.)
[ ] If real values are unavoidable (e.g., tenant-level constants), document them clearly
[ ] Example README explains how to use the example
```

### 5e: Security

```
[ ] Secrets stored in Key Vault (not as plaintext variables)
[ ] Identity/credential variables accept KV secret NAMES, not raw values
    - var.identity.client_id should be a KV secret name, not the actual client ID
    - Module resolves credentials via data "azurerm_key_vault_secret" at apply time
[ ] Public access disabled by default
[ ] Entra RBAC preferred over local admin/access keys
[ ] Managed Identity preferred over Service Principal
[ ] No credentials hardcoded or defaulted
[ ] identity variable — only genuinely sensitive fields marked sensitive
[ ] Network access restricted by default (private endpoints, firewalls)
[ ] Encryption at rest enabled by default where applicable
```

### 5f: Pre-commit and Tooling

```
[ ] .pre-commit-config.yaml includes: terraform_fmt, terraform_validate, terraform_docs, terraform_tflint
[ ] No hooks for tools not used in the repo (shellcheck without .sh files, etc.)
[ ] All hooks point to current versions (not pinned to very old versions)
```

## After All Passes

### Synthesize Findings

1. **Deduplicate.** If the same underlying issue manifests in multiple places, report it once with all affected locations, not as separate findings.
2. **Calibrate severity.** Review all findings and verify severity is consistent. All count-guard issues are Critical. All standard-variable deviations are Major.
3. **Check for cascading issues.** Does fixing one finding automatically fix others? Note these relationships.
4. **Identify positive patterns.** What did the developer do well? Call it out specifically.

### State the Verdict

| Verdict | When to Use |
|---------|-------------|
| **Approve** | No Critical or Major findings. All Minor findings are truly minor. |
| **Approve with Comments** | No Critical findings. Major findings are limited to style/convention deviations that don't affect runtime behavior. |
| **Request Changes** | Any Critical findings, OR 3+ Major findings, OR Major findings that affect consumer experience. |
| **Needs Major Revision** | Fundamental architecture issues. Wrong responsibility boundaries. Missing entire feature areas. Needs redesign. |

### The Final Compliance Check

Before submitting your review, ask yourself:

1. Did I question every data source and explain why it shouldn't be a variable input?
2. Did I trace every boolean toggle to verify the entire conditional chain is guarded?
3. Did I verify the exact standard variable/local patterns are used (not approximations)?
4. Did I check that the merge order for tags is correct?
5. Did I verify no `lower()`/`upper()` wrapping on already-validated inputs?
6. Did I check that the module doesn't create SPNs or manage role assignments directly?
7. Did I verify the example is simple, complete, and actually runnable?
8. Did I provide exact code fixes for every Critical and Major finding?
9. Did I acknowledge what the developer did well?
10. Would I be comfortable defending every severity rating I assigned?
11. Did I trace bad defaults/inputs through locals to their runtime impact before setting severity?
12. Did I verify credentials go through Key Vault (not as plaintext variable values)?
13. Are my findings atomic — one problem per finding, not bundled mega-findings?
14. Are formatting-only issues (periods, heredoc style) correctly rated as Minor, not Major?

If you can answer yes to all of these, submit the review.
