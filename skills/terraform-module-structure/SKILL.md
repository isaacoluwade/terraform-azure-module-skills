# Terraform Module Structure

A Terraform Azure module is a directory of files following a predictable layout. Get the layout right and every other concern — variables, outputs, tests, docs, CI — has an obvious home. Get it wrong and reviewers waste cycles asking "where does this go?" on every PR.

This skill defines *the layout*. Sibling skills own per-file content:

- `terraform-variable-design` — `variables.tf`
- `terraform-locals-patterns` — `locals.tf`

- `terraform-module-testing` — `terratest/`

## Standard Module Tree

Every certifiable Azure Terraform module follows this layout:

```
.
├── docs/                           # Service documentation
│   ├── images/
│   │   ├── <service>.drawio        # Architecture diagram source
│   │   └── <service>.drawio.png    # Architecture diagram image
│   └── ServiceDoc-<service>.md     # Service documentation
├── examples/                       # Usage examples
│   ├── main/                       # Basic usage example (required)
│   │   ├── locals.tf
│   │   ├── main.tf
│   │   ├── outputs.tf
│   │   ├── variables.tf
│   │   └── versions.tf
│   └── <use-case>/                 # Optional: complex/advanced examples
│       ├── locals.tf
│       ├── main.tf
│       ├── outputs.tf
│       ├── variables.tf
│       └── versions.tf
├── terratest/                      # Infrastructure tests
│   ├── plan/
│   │   ├── main.tf
│   │   ├── outputs.tf
│   │   ├── variables.tf
│   │   └── versions.tf
│   └── test/
│       ├── go.mod
│       ├── go.sum
│       └── terraform_test.go
├── .gitignore
├── .pre-commit-config.yaml         # Pre-commit hook configuration
├── azure-pipelines.yml             # CI/CD pipeline
├── CHANGELOG.md                    # Version history
├── README.md                       # Auto-generated by terraform-docs
├── VERSION                         # SemVer version number
├── locals.tf                       # Local values
├── main.tf                         # Primary resource(s)
├── <logical-group>.tf              # Grouped resources (diagnostics.tf, privatelink.tf, ...)
├── outputs.tf                      # Module outputs
├── variables.tf                    # Input variables
└── versions.tf                     # Provider and Terraform version requirements
```

### Why this layout

- **`docs/`** keeps service documentation and architecture diagrams versioned alongside the code so reviewers can find them immediately.
- **`examples/`** gives consumers something runnable. A mandatory `main/` example lowers the barrier to adoption; additional use-case directories keep the basic example uncluttered.
- **`terratest/`** holds plan-level tests that catch regressions before merge. `plan/` is the Terraform configuration; `test/` is the Go-based assertion code.
- **Root `.tf` files** are split by purpose. Terraform loads every `.tf` file in a directory regardless of name, so the split is purely for human readability — `main.tf`, `variables.tf`, `outputs.tf`, `locals.tf`, `versions.tf`, plus logical-grouping files for cohesive concerns.

## Root `.tf` Files

| File           | Contents                                              |
| -------------- | ----------------------------------------------------- |
| `main.tf`      | The primary resource(s) the module exists to create   |
| `variables.tf` | Input variable declarations                           |
| `outputs.tf`   | Module outputs (always plural)                        |
| `locals.tf`    | Local values: standard locals + module-specific ones  |
| `versions.tf`  | `terraform` block, `required_providers`, version pins |

The split is enforced not by Terraform but by team convention. A reviewer opening any module knows exactly where to find each concern, and diffs stay focused — a change to a variable description doesn't ripple into the file holding the resource.

## The `main` Resource Label

The primary resource in `main.tf` is always labelled `main`:

```hcl
resource "azurerm_redhat_openshift_cluster" "main" {
  name                = local.cluster_name
  location            = var.location
  resource_group_name = var.resource_group_name
  # ...
}
```

A consistent `main` label across every module creates a predictable mental model. When reading any module, you know `azurerm_<type>.main` is the central resource — code reviews are faster and cross-module navigation is intuitive. Test code, outputs, and importing all benefit from this consistency.

### Resource Block Attribute Ordering

Within a resource block, order attributes for readability:

1. **Meta-arguments** — `count`, `for_each`, `provider`
2. *(empty line)*
3. **Single-line properties** — scalars like `name`, `location`, `sku_name`
4. *(empty line)*
5. **Nested blocks** — `network_profile {}`, `identity {}` (separated by empty lines if multiple)
6. **Lifecycle meta** — `lifecycle {}`, `depends_on`, `provisioner`

```hcl
# Good — clear visual separation
resource "azurerm_kubernetes_cluster" "main" {
  for_each = local.clusters

  name                = each.value.name
  location            = var.location
  resource_group_name = var.resource_group_name
  dns_prefix          = each.value.dns_prefix

  default_node_pool {
    name       = "default"
    node_count = each.value.node_count
    vm_size    = each.value.vm_size
  }

  identity {
    type = "SystemAssigned"
  }

  lifecycle {
    ignore_changes = [default_node_pool[0].node_count]
  }
}

# Bad — blocks mixed with single-line properties
resource "azurerm_kubernetes_cluster" "main" {
  name     = "example"
  identity {
    type = "SystemAssigned"
  }
  location            = var.location
  resource_group_name = var.resource_group_name
  default_node_pool {
    name = "default"
  }
}
```

## Logical-Grouping Files

When a module manages a cohesive set of related resources beyond the primary resource, move them to a separate `.tf` file named after the concern:

| File             | Contents                              |
| ---------------- | ------------------------------------- |
| `diagnostics.tf` | Diagnostic settings                   |
| `privatelink.tf` | Private endpoint and DNS zone records |
| `infoblox.tf`    | Infoblox DNS records                  |
| `vault.tf`       | Key Vault secrets and access policies |
| `rbac.tf`        | Role assignments                      |
| `network.tf`     | Subnet, NSG, route table associations |

**Use descriptive conventional names, not abbreviations.** `keyvault.tf` is better than `akv.tf` — the filename should be immediately recognizable to anyone on the team.

Grouping by concern (rather than by resource type) mirrors how teams think about infrastructure. A developer debugging DNS issues opens `infoblox.tf` directly instead of scrolling through a monolithic `main.tf`. PR diffs stay focused — changes to diagnostics don't pollute the diff for the primary resource.

### Prefer raw resources over module wrappers for single resources

When only a single resource is involved, use the resource directly rather than wrapping it in a helper module — there is no benefit to an extra module for one resource.

```hcl
# Good — direct resource for a simple operation
resource "azurerm_key_vault_secret" "main" {
  for_each     = var.secrets
  name         = each.key
  value        = each.value
  key_vault_id = var.key_vault_id
}

# Bad — unnecessary module wrapper for a single resource
module "keyvault_secret" {
  source       = "<your-terraform-registry>/keyvault-secret/azurerm"
  for_each     = var.secrets
  name         = each.key
  value        = each.value
  key_vault_id = var.key_vault_id
}
```

## Examples Directory

Always include at least one example under `examples/main/`. Add additional directories (`examples/replication/`, `examples/private/`, etc.) for advanced or non-default scenarios. Add a new example whenever the module gains a feature that materially changes how consumers call it.

Each example directory mirrors the root layout: `main.tf`, `locals.tf`, `variables.tf`, `outputs.tf`, `versions.tf`. Examples should use the `locals {}` pattern to centralize tuneable inputs at the top of `main.tf` rather than scattering literals through resource blocks.

### Example variables must be minimal

Variables in `examples/*/variables.tf` are simple empty declarations — no types, descriptions, or defaults. These are consumer-facing examples, not module definitions:

```hcl
# Good — minimal example variable declarations
variable "brand" {}
variable "project_name" {}
variable "projectcode" {}
variable "costcenter" {}
variable "environment" {}
variable "location" {}
variable "resource_group_name" {}

# Bad — over-specified example variables
variable "brand" {
  description = "The brand identifier for resource naming"
  type        = string
  default     = "acme"
  validation {
    condition     = length(var.brand) <= 5
    error_message = "Brand must be 5 chars or less."
  }
}
```

### No provider credentials in examples

Examples must never declare Azure credential variables (`client_id`, `client_secret`, `ARM_*`). Rely on the workspace environment variables the provider already supports: `ARM_SUBSCRIPTION_ID`, `ARM_TENANT_ID`, `ARM_CLIENT_ID`, `ARM_CLIENT_SECRET`. Provider blocks reference only `subscription_id` and `tenant_id`:

```hcl
# Good — examples/main/providers.tf
provider "azurerm" {
  subscription_id = var.subscription_id
  tenant_id       = var.tenant_id
  features {}
}

# Bad — embedding auth config in example
provider "azurerm" {
  subscription_id = var.azure_subscription_id
  client_id       = var.azure_client_id
  client_secret   = var.azure_client_secret
  tenant_id       = var.azure_tenant_id
  features {}
}
```

### Pin provider versions in examples

Examples should pin `azurerm` to an exact version for production stability. Inline comments explaining version choices are welcome — they help consumers:

```hcl
required_providers {
  azurerm = {
    source  = "hashicorp/azurerm"
    version = "4.65.0" # Pin to exact version for production environments
  }
  azapi = {
    source  = "Azure/azapi"
    version = "~> 2.0"  # Limit to minor versions
  }
}
```

### Example values and placeholders

Use `var.x` references wherever possible. For values that cannot use variables (e.g., a hardcoded resource ID inside `locals`), use `{placeholder}` or `<placeholder>` syntax to signal a non-constant value. Never embed real CIDRs, subscription IDs, or resource IDs in example code.

Use `"example-"` as the prefix for name values, never `"test-"`:

```hcl
# Good
locals {
  apps_subnet_id = "/subscriptions/{subscriptionID}/resourceGroups/{resourceGroupName}/providers/Microsoft.Network/virtualNetworks/{vnetName}/subnets/{subnetName}"
}

subnets = {
  example_subnet = {
    subnet_name = "example-snet"
  }
}

# Bad — real values, "test" prefix
locals {
  resource_group_id = "/subscriptions/b871a584-5cc1-46e7-ada8-a1bac91dc8d1/resourceGroups/my-rg/"
}
subnets = { test_subnet = { subnet_name = "test-snet-01" } }
```

### Keep examples focused

Provide exactly what is required to demonstrate the module — do not overload examples with peripheral resources. Write examples as if the consumer is a junior engineer with little Terraform experience. Do not show `name_override` in examples; it exists only for importing existing resources or migration work, and consumers should follow the default naming convention.

## Terratest Directory

The `terratest/` directory holds plan-level tests:

```
terratest/
├── plan/                # Terraform configuration that exercises the module
│   ├── main.tf
│   ├── outputs.tf
│   ├── variables.tf
│   └── versions.tf
└── test/                # Go-based Terratest assertions
    ├── go.mod
    ├── go.sum
    └── terraform_test.go
```

### Use the standard test framework

Use `<your-terratest-helpers>` and its latest version. Do not write fully custom test configurations. If functionality is missing from the framework, contribute it upstream rather than implementing one-off logic in a single module.

### Focus tests on the core module path

Terratest plans should exercise the core module functionality only. Do not include optional or peripheral infrastructure (jumpbox resource groups, ancillary networking) that adds execution time without improving module validation.

### Plan structure: values in locals, pass-through in main

In `terratest/plan/main.tf`, module calls should only pass through values defined in `terratest/plan/locals.tf`. Do not compute values, embed literals, or use data source lookups in the module call:

```hcl
# Good — terratest/plan/main.tf (pass-through only)
module "aro" {
  source = "../../"

  for_each = local.aro

  brand               = var.brand
  environment         = var.environment
  costcenter          = var.costcenter
  projectcode         = var.projectcode
  network             = local.network
  cluster             = local.cluster
  resource_group_name = var.resource_group_name
}

# Bad — computing values inline
module "aro" {
  source = "../../"

  network = {
    vnet_name = data.azurerm_virtual_network.main.name
    pod_cidr  = "10.128.0.0/14"
  }
}
```

This rule keeps the module call boring and the test inputs explicit. All "what does the test exercise" lives in `locals.tf`; `main.tf` just wires it through.

For the contents of `terraform_test.go` and assertion patterns, see `terraform-module-testing`.

## Scripts Directory

Custom scripts go under `scripts/`. **Use scripts only when functionality is not available in the AzureRM or AzApi providers** — they are a last resort. Always prefer native Terraform resources, and always consider the destroy event when using `local-exec` provisioners (if a script creates an external resource, a corresponding destroy-time provisioner or out-of-band cleanup must exist). Switch to Terraform resources when provider functionality becomes available.

Scripts introduce hidden state that Terraform cannot track. They break `terraform plan` accuracy, complicate `terraform destroy`, and make modules harder to test. Keeping them in `scripts/` at least makes their existence visible.

## Deprecated Files

When deprecating a variable or output during a minor or patch release, do not delete it immediately — move it to a deprecated file:

- **`deprecated_variables.tf`** — deprecated variables, `DEPRECATED` prefix in description
- **`deprecated_outputs.tf`** — deprecated outputs, `DEPRECATED` prefix in description

Clean up both files during the next major version release.

```hcl
# deprecated_variables.tf
variable "vnet_rg" {
  description = "DEPRECATED: Use `resource_group_name` instead."
  type        = string
  default     = null
}

# deprecated_outputs.tf
output "aro_cluster_id" {
  description = "DEPRECATED: Use `cluster_id` instead."
  value       = azurerm_redhat_openshift_cluster.main.id
}
```

Updated tree with deprecated files in place:

```
.
├── ...
├── deprecated_outputs.tf           # Clean up on next major
├── deprecated_variables.tf         # Clean up on next major
├── locals.tf
├── main.tf
├── outputs.tf
├── variables.tf
└── versions.tf
```

This pattern lets consumers migrate at their own pace while clearly signalling the migration path.

## Supporting Files

### `.gitignore`

Every module repository must include a `.gitignore` with these patterns:

```gitignore
# Terraform state (never commit)
*.tfstate
*.tfstate.backup
*.tfstate.*.backup

# Terraform working directory
.terraform/

# Terraform plan files
*.tfplan

# Sensitive variable files
*.auto.tfvars
!*.auto.tfvars.example

# OS files
.DS_Store
Thumbs.db
```

**Always commit:** `.terraform.lock.hcl`, all `.tf` files, `.pre-commit-config.yaml`. The lock file pins exact provider versions (with hashes) — without it, `terraform init` may download different provider builds on different machines, causing subtle drift.

### `VERSION`, `CHANGELOG.md`, `README.md`

`VERSION` holds the SemVer number — without bumping it, the new version will not be published to the registry. `CHANGELOG.md` follows Keep a Changelog format with `### Added`, `### Changed`, `### Fixed`, `### Removed` sections; use `**Breaking:**` to flag breaking changes. `README.md` is auto-generated by `terraform-docs` from variables, outputs, and the header comment in `main.tf` — do not hand-edit it. See `terraform-module-documentation` for content rules.

### `azure-pipelines.yml`

A thin pipeline definition that delegates to shared YAML templates from `<your-pipeline-templates>`. The template handles validation, plan, terratest, and publish steps. Keep the per-module pipeline file short — most logic should live in the templates.

## Pre-commit Configuration

Every module must include a `.pre-commit-config.yaml` running these standard hooks. Use the latest versions:

```yaml
repos:
  - repo: https://gitlab.com/vojko.pribudic.foss/pre-commit-update
    rev: v0.9.0
    hooks:
      - id: pre-commit-update

  - repo: https://github.com/terraform-docs/terraform-docs
    rev: v0.21.0
    hooks:
      - id: terraform-docs-go
        args:
          - "markdown"
          - "table"
          - "--output-mode"
          - "replace"
          - "--output-file"
          - "README.md"
          - "--output-template"
          - "{{ .Content }}\n"
          - "."

  - repo: https://github.com/jumanjihouse/pre-commit-hook-yamlfmt
    rev: 0.2.3
    hooks:
      - id: yamlfmt
        args: [--mapping, '2', --sequence, '4', --offset, '2']
```

What each hook does:

- **`pre-commit-update`** — keeps the hook revisions themselves up to date so the toolchain doesn't rot.
- **`terraform-docs-go`** — regenerates `README.md` from variables, outputs, and the header comment in `main.tf` on every commit. This is what makes `README.md` a generated artifact rather than something humans hand-maintain.
- **`yamlfmt`** — normalizes YAML indentation across pipeline files and the pre-commit config itself.

Standardizing pre-commit across modules ensures consistent README generation, YAML formatting, and automatic hook updates without the team needing to think about it.

## Common Mistakes

1. **Resource label other than `main`** for the primary resource — breaks the cross-module mental model and complicates test code.
2. **Monolithic `main.tf`** holding diagnostics, private endpoints, and DNS records alongside the primary resource. Split them into `diagnostics.tf`, `privatelink.tf`, etc.
3. **Abbreviated logical-grouping filenames** like `akv.tf` or `pe.tf` instead of `keyvault.tf` or `privatelink.tf`.
4. **Wrapping a single resource in a helper module** when a direct `resource` block would do.
5. **Missing `examples/main/`** — every module must have a runnable basic example.
6. **Over-specified example variables** — examples don't need types, descriptions, defaults, or validations on their input variables.
7. **Auth credentials in example variables** (`client_id`, `client_secret`) — examples must rely on `ARM_*` environment variables.
8. **Loose provider version constraints in examples** like `>= 4.0` — pin to an exact version so consumers copying the example get a known-good baseline.
9. **Computing values inline in `terratest/plan/main.tf`** — the module call must be a pass-through; values belong in `terratest/plan/locals.tf`.
10. **Deleting deprecated variables/outputs in a non-major release** instead of moving them to `deprecated_variables.tf` / `deprecated_outputs.tf`.
11. **Not committing `.terraform.lock.hcl`** — leads to non-reproducible provider versions across the team.
12. **Hand-editing `README.md`** — it's a generated artifact; edits will be overwritten by the next `terraform-docs` run.
13. **Missing `.pre-commit-config.yaml`** — without it, `README.md` falls out of sync with the module and YAML formatting drifts.

## Review Checklist

- [ ] All five core root files exist: `main.tf`, `variables.tf`, `outputs.tf`, `locals.tf`, `versions.tf`.
- [ ] The primary resource in `main.tf` uses the label `main`.
- [ ] Cohesive resource groups are split into named `.tf` files (`diagnostics.tf`, `privatelink.tf`, etc.) with conventional, non-abbreviated names.
- [ ] Resource block attributes follow meta-args → scalars → nested blocks → lifecycle order, separated by blank lines.
- [ ] `examples/main/` exists and is runnable; complex scenarios have their own subdirectory.
- [ ] Example `variables.tf` files contain only empty declarations.
- [ ] Examples use `ARM_*` env vars for credentials; no `client_id`/`client_secret` variables.
- [ ] Examples pin `azurerm` to an exact version.
- [ ] `terratest/plan/main.tf` is pass-through only; all values come from `terratest/plan/locals.tf`.
- [ ] Deprecated variables/outputs live in `deprecated_variables.tf` / `deprecated_outputs.tf` with `DEPRECATED:` prefixes.
- [ ] `.gitignore` excludes state, `.terraform/`, `*.tfplan`, and `*.auto.tfvars`; `.terraform.lock.hcl` is committed.
- [ ] `VERSION`, `CHANGELOG.md`, `README.md` are present; `README.md` is generated by `terraform-docs`.
- [ ] `.pre-commit-config.yaml` includes `pre-commit-update`, `terraform-docs-go`, and `yamlfmt` hooks at current versions.
- [ ] `azure-pipelines.yml` delegates to shared templates rather than duplicating CI logic.
- [ ] `scripts/` exists only when no provider equivalent is available, and any `local-exec` has a destroy-time counterpart.
